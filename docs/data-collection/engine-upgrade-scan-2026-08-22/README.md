## 설계 평가가 내린 순위 (공수·위험 포함 — findings.json design 절)

1. **건당 최소금액·횟수 필드**(minPerTx·maxUsesPerMonth·perUseCap) + 태그별 객단가 기준값 — 과대 175행 해소, 최대 규모. 규약 §1의 환산 기준(주유 1,850원/L·교통 1,550원/건) 방식과 일관.
2. **옵션 팩 프로필**(B-6) — 팩 조합 열거 후 최유리 팩 채택. 12장 재인코딩 필요(팩 안 한도가 '영역별'인지 '통합'인지 원문 재확인이 관건 — 혼동하면 반대 방향 오류).
3. **소품 3종(공수 소)**: requiresTag 게이트(shinhan-edu 유령 월 5천원), 프로모션 validUntil(잔여 개월 비례 축소), nh-20-haebom 통신비 sharedCaps 이관(데이터만).
4. **같은 태그 복수 행 허용**(B-2) — 그리디 지출 배분 필수(안 하면 B-5 재림). 일부는 팩 프로필(2번)이 선행돼야 살아남.
5. **요일·시간대 가중치** — 주말 2/7 같은 가정치 필요.
6. **결제수단 질문화**(B-4) — 페이 1문항 + 조건부 요율 필드. 양방향 100행 안팎 정합, 단 '3분 컷' UX와 충돌하고 시작하면 전수(74행+α)를 끝까지 가야 함.
- **부결**: 유령 행(태그 밖 sharedCap 소진 반영) — 가정 지출이 §0-2 위반이고 '달성 가능한 최대' 의미론과 충돌. 대신 SharedCap.alsoUsedBy 표시 필드만 권고.
- **보류**: 3단 한도 직교화(실수요 카드 0장), 총액 상한 그리디 배분(전 카드 미세 변동 대비 순위 영향 작음).

- 과소(카드에 불리)만 남은 게 아니다 — **과대(사용자에게 거짓 약속) 쪽이 더 크게 남아 있다**: ①의 175행, ③의 43행, ②의 2장.
