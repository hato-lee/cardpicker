# 2단 한도(sharedCaps) 엔진 확장 + 인코딩 (2026-08-22)

OPEN-ISSUES **B-1** 해결. "영역별 월 5천원, 단 전체 통합 월 2만원" 같은 **2단 구조**를 표현할 수 있게 됐다.

- `verification-round1.json` — 후보 50장 원문 대조 결과
- `verification-round2.json` — 1차 키워드 스캔이 놓친 17장 (전부 현행 유지)
- `cross-review.md` — 채택안 교차 검토(패치본을 만들어 `validateCards()`까지 돌린 기록)

## 새 스키마

```jsonc
{
  "sharedCaps": { "life": { "monthlyCap": 20000, "tiers": [{ "minSpend": 600000, "monthlyCap": 40000 }] } },
  "benefits": [
    { "tag": "통신비", "rate": 10, "monthlyCap": 5000, "sharedCapGroup": "life", ... },
    { "tag": "마트·장보기", "rate": 10, "monthlyCap": 5000, "sharedCapGroup": "life", ... }
  ]
}
```

계산 순서: **줄 한도 → capGroup 축소 → sharedCap 축소 → 총액 상한.**

`capGroup`과 다르다 — `capGroup`은 줄들이 한도 **하나**를 나눠 쓰는 구조(영역별 한도가 따로 없다),
`sharedCapGroup`은 줄마다 **제 한도가 있고** 그 위에 **합계 천장**이 또 있는 구조다. 둘을 같이 쓸 수 있다.

제약: 한 그룹에 혜택 **2개 이상**, **type 동일**(상한 단위가 원/마일로 갈리므로), tiers는 카드 minSpend 초과.
**통합 상한이 영역 한도 합계 이상이면 넣지 않는다** — 아무 일도 안 일어나고 복잡도만 는다.

## 절반은 "통합값이 줄에 새어들어 있던" 카드였다

2단을 표현 못 하던 시절의 우회로, **통합 한도 값을 줄의 `monthlyCap`에 대신 써 넣은** 카드들이 있었다.
그대로 두고 천장만 얹으면 영역 한도가 부푼 채로 남는다 — **천장을 얹는 것보다 이걸 되돌리는 게 본체다.**

현대 알파벳 5형제가 대표적이다. 원문은 세 카드가 글자 하나 다르지 않게

> `- 40만원 이상 80만원 미만 : 영역별 월 5천원, 대상 영역 통합해 월 5천원`
> `- 80만원 이상 120만원 미만 : 영역별 월 5천원, 대상 영역 통합해 월 1만원`
> `- 120만원 이상 : 영역별 월 5천원, 대상 영역 통합해 월 1만 5천원`

인데, **영역 한도에까지 통합 tiers가 붙어** 있었다. 그래서 카페 하나만 고른 사용자에게 월 1.5만원(실제 5천원)이 잡혔다.

| hyundai-alphabet-s · 월 지출 | 카페만 (전 → 후) | 4영역 (전 → 후) |
|---|---|---|
| 50만 | 5,000 → 5,000 | 5,000 → 5,000 |
| 100만 | **10,000 → 5,000** | 10,000 → 10,000 |
| 150만 | **15,000 → 5,000** | 15,000 → 15,000 |

## 영향

3,360개 조합 중 **34개가 내려갔고 오른 것은 없다.** 빠른 길 프리셋 1개(`차 끌고 출퇴근`)에서 TOP5가 바뀌었다.
`bc-baro-macao`만 주유와 장보기를 함께 고를 때 오르는데, 원문 표가 주유와 장보기를 **별개 영역으로 명시**하는데도
한 그룹으로 묶여 있던 과소가 풀린 것이다(10,000 → 12,000).

## 교차 검토가 후보 밖에서 찾아낸 것

첫 스캔이 놓친 카드 4장을 교차 검토 에이전트가 memo에서 찾아냈다.

- `woori-everyday-check` — **채택**. 원문 표의 통합 셀이 `rowspan=5`로 5영역을 덮고,
  「'통합 월 한도' 및 '각 영역별 적립한도' 중 하나의 한도를 초과한 이후 결제한 건에 대해서는 기본 적립 혜택 제공」이라는
  카드사 문장이 두 한도의 공존을 못 박는다. 다만 총액 상한이 함께 걸려 **월 300만원 이상 고지출 + 6영역 전부 선택**에서만
  값이 내려간다(27,632 → 20,000).
- `kb-you-prime` — **해당 없음**. memo의 "엔진 sharedCap 확장 시 재검토"가 오해를 부른 경우다.
  이 카드의 `capGroup: "pack"`은 한도 공유가 아니라 **택1 배타성**을 표현한 것이라 sharedCaps로 대체할 수 없다
  (팩 통합 한도는 원문에 아예 없다). OPEN-ISSUES **B-6**으로 따로 올렸다.
- `shinhan-hey-young-check` — 단종 카드. `bc-baro-green-card` — 통합값이 영역 합계와 같아 무동작.

## 넣지 않은 것

- **통합 상한이 영역 합계와 같은 카드** — `nh-allone-pi`(3,000+2,000=5,000), `bc-baro-clear-plus`,
  `kb-nori2-kbpay`(태그 행 합 15,500 < 20,000), `shinhan-discount-plan-plus`, `samsung-id-on`, `samsung-id-move` 등 38장.
  memo의 "카드 전체 통합한도"가 **하위 한도의 산술합을 오독한 것**인 경우가 많았다.
- `shinhan-hey-young-check` — 문서 B-1의 대표 예시였지만 **단종 카드**라 추천에 안 뜬다.
- `nh-zgm-playplus` — 형식상 2단이지만 온·오프라인 택1이라 넣으면 오히려 부풀어난다.
- `kb-goldenlife-olim` — 팩 택1을 sharedCap으로 누르자는 아이디어는 그 숫자가 원문에 없어 §0 위반이라 기각.

## 남는 한계

- sharedCap은 **사용자가 고른 태그의 행에만** 걸린다. 같은 풀을 쓰는 태그 밖 혜택
  (`ibk-kpass-check` 영화 4천, `nh-zgm-discount` 보험, `hana-tossbank-day` 보험·골프)은 계산에 안 들어가 실제보다 낙관적이다.
- 한 줄은 sharedCapGroup을 **하나만** 가질 수 있어 3단 이상은 표현 못 한다.
- `bc-baro-onoff`의 대중교통·택시는 원문상 한 영역인데 monthlyCap이 4,000/5,000으로 달라 capGroup으로 못 묶는다
  (더 크게 작용하는 통합 상한 쪽을 택했다).
