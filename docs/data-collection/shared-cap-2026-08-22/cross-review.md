# ② 기각·보류한 제안과 이유

## 기각한 것 없음 — 38건의 `already-ok`는 전부 타당

교차 검증에서 특히 확인한 4가지 “안 넣는 게 맞는” 판정:

| 카드 | 이유 | 직접 검산 |
|---|---|---|
| `nh-allone-pi` | 라이프 '총 할인한도'가 하위 한도의 **정확한 합** | 3,000+2,000=5,000 ✓ / 6,000+4,000=10,000 ✓ → 무동작 |
| `bc-baro-clear-plus` | 통합 = 매일+라이프스타일 정확한 합 | 2,500+2,500=5,000 ✓ 등 → 무동작 |
| `kb-nori2-kbpay` | 진짜 2단이지만 **우산이 구속하지 않음** | 태그 행 합 최대 15,500 < 최저 구간 20,000 ✓ |
| `shinhan-discount-plan-plus` | 카드 전체 '월 최대 혜택 한도'가 Plan 합계 이상 | 수록분 합 25,000/45,000/65,000/90,000 < 30,000/50,000/73,000/100,000 ✓ |

`shinhan-lottemart-maxx`·`hana-wonder2-free-plus`는 2단이 실재하나 **태그 안 멤버가 1개뿐**이라 스키마상 `sharedCapGroup` 구성 불가(≥2 강제) — 그 행의 monthlyCap이 곧 통합값이라 결과도 동일합니다. 판정 일관됨.

## 판정 기준 일관성 — 어긋난 곳 없음

- 알파벳 5형제(S/R/B/O/H)가 **전부 동일하게** two-level + rowCapFixes 처리됨. 원문이 문구 단위로 같음을 확인했습니다.
- “통합 ≥ 합계면 안 넣는다”가 `nh-allone-pi`·`bc-baro-clear-plus`·`kb-nori2-kbpay`·`shinhan-discount-plan-plus`·`nh-byeoldajul`에 일관 적용.
- “한 구간이라도 물리면 넣는다”가 `hyundai-h`·`alphabet-o`(최저 구간만)·`hana-tossbank-day`(최고 구간만)·`ibk-kpass-check`(최저 구간만)에 일관 적용.

## 함께 적용하면 안 되는 별건 제안 (보류)

- **`shinhan-point-plan-plus`** — '모든 가맹점'과 '해외 결제'를 capGroup으로 묶자는 제안. 값이 동일해 스키마는 통과하지만, **엔진의 universal 경로에는 capGroup이 전달되지 않습니다**(`makeRow({tag:'모든 가맹점', ...card.universal})` — universal 객체에 capGroup 필드가 없음). '모든 가맹점' 태그를 직접 고른 사용자에게만 그룹이 걸리는 반쪽 효과라, 엔진 쪽 결정이 먼저입니다. 이번 배치에서 빼는 것에 동의.
- **`kb-goldenlife-olim`** — Golden Choice 택1을 sharedCapGroup으로 누르자는 아이디어를 §0(지어내지 않는다)으로 스스로 기각한 판단이 옳습니다. 배타 그룹은 엔진 사안.

# ④ 적용 시 주의사항

1. **rowCapFixes와 sharedCaps는 반드시 한 커밋에 같이 넣어라.** 알파벳 S/R/B에서 행 tiers만 지우고 sharedCaps를 안 넣으면 40만 구간에서 4행 합이 15,000(실제 5,000)이 되어 **지금보다 3배 나빠집니다.** `hyundai-h`·`alphabet-o`도 같은 함정(10,000 vs 실제 5,000).
2. **capGroup 제거 범위를 헷갈리지 마라.** 알파벳 S/R/B는 카페·편의점에서만 제거하고 대중교통·택시 두 줄에는 **남깁니다**(원문상 한 영역). 반대로 `hyundai-h`·`alphabet-o`는 두 줄이 **서로 다른 영역**이라 완전히 제거합니다. `bc-baro-macao`는 주유만 빼고 마트+온라인은 남깁니다.
3. **스키마는 전부 통과함(검증 완료).** 패치본을 만들어 `validateCards()`를 돌렸고, 통과했습니다. 확인한 항목: sharedCapGroup 멤버 ≥2(최소 2, 최대 7) / 전부 동일 type(모두 `discount`) / sharedCaps.tiers의 minSpend가 카드 minSpend 초과(40만 카드에 80만·120만, 30만 카드에 50만·60만·100만 등) / 남는 capGroup의 monthlyCap·tiers 동일.
4. **stars는 재계산 불필요.** §8 기준은 “최저 실적구간의 기본값”인데, 되돌리는 행은 전부 base monthlyCap 5,000이 그대로이고 rate도 그대로라 ★2가 유지됩니다(tiers만 삭제).
5. **`bc-baro-macao`만 값이 올라간다.** 12건 중 유일한 상향(+2,000~5,000/월)이므로, §0 관점에서 적용 전에 BC 공식 `cardGdsNo=101010` 한도표를 한 번 더 눈으로 확인하는 편이 안전합니다(고릴라 2728 원문에서는 `영역(주유/장보기)별 한도` 표기를 제가 확인했습니다).
6. **`sharedCaps` 정의만 넣고 `sharedCapGroup`을 안 붙이면 스키마가 막습니다**(“sharedCaps 'x'을 쓰는 혜택이 없습니다”). 반대도 마찬가지. 짝을 맞춰 넣으세요.
7. **엔진은 사용자가 고른 태그의 행만 만든다** — sharedCap은 “고른 태그들 합계”에만 걸립니다. 그래서 태그 밖 혜택이 같은 풀을 쓰는 카드는 여전히 낙관적이고, 이는 §③(b)에 남겨 둔 잔여 한계입니다.
8. **`nh-zgm-discount`의 `basic` 그룹(모든 가맹점·해외 결제)은 절대 `life`에 넣지 말 것** — 원문상 기본할인과 생활할인은 별개 트랙입니다(게다가 서로 중복 미적용이라 이미 별개 과대 요인이 있음).
