# 건당·횟수 조건 반영 (2026-08-22)

`engine-upgrade-scan-2026-08-22`이 1순위로 꼽은 항목. "건당 1만원 이상 · 월 2회 · 1회 2천원까지" 같은 조건을
note로만 두어 **한도를 회차로 다 못 채우는 혜택이 한도 전액으로 계산되던 과대**를 없앴다.

- `baseline-research.json` — 태그별 대표 건당 결제금액(TXN_SIZE) 근거 조사 4갈래 + 엔진 설계 검토 2건 + 종합
- `decisions.json` — 후보 303행 전수 인코딩 결정(encode 189 / skip 115)
- `reduced-rows.txt` — 실제로 한도가 줄어든 47행과 그 근거 note 원문

규약은 `ENCODING-RULES.md` **§10**이 정본. 엔진은 `benefit.ts`의 `perTxValueOf`·`effectiveCapOf`·`applyUseGroups`.

## 처음 세운 설계가 틀렸고, 조사가 그걸 뒤집었다

처음 계획은 **"객단가가 문턱보다 작으면 그 혜택은 0"**(게이트)이었다. 세 가지가 반박했다.

1. **폴백이 없는 카드가 64%다**(active 224장 중 143장 = universal 없음 101 + 마일리지형 universal 42).
   `annualBenefit`은 줄이 하나도 안 남으면 0원이 아니라 **`null`을 반환해 카드가 후보에서 사라진다.**
   카페만 골랐을 때 19장이 증발할 뻔했다.
2. **평균 객단가는 '평균 결제 1건'이지 '그 달 가장 큰 결제 1건'이 아니다.** 월 3회 조건은 카페 결제 27건 중
   3건만 문턱을 넘으면 충족된다.
3. **전제 자체가 사실이 아니었다.** '커피 객단가 5~6천원'은 저가 브랜드 **음료 1잔 값**이지 카드 1건 결제액이 아니다.
   카드결제 패널 실측은 7,200~7,736원, 스타벅스는 12,945원. 같은 자료의 분포 — 저가 5사는 결제의 **91~94%가 1만원 미만**,
   스타벅스·투썸 등은 **42~48%가 1만원 이상**. '건당 1만원' 조건의 값어치는 0도 전액도 아니다.

→ **`minPerTx`는 게이트가 아니라 '이 줄의 건당 결제액'**이 됐고, 값을 실제로 줄이는 것은 **`maxUsesPerMonth`**다.

## 결과

**5,622개 조합 중 202개가 내려갔고 오른 것은 0개, 사라진 카드도 0장이다.** 44개 질의 중 18개에서 TOP5가 바뀌었다.
`cards.test.ts`가 "이 기능으로 값이 오르는 행은 없다"를 전 카드에서 강제한다 — 오르면 그 카드의 인코딩이 틀린 것이다.

가장 크게 내린 것들:

| 카드 / 태그 | 전 → 후 (연) | 근거 |
|---|---|---|
| 신한 Discount Plan+ / 택시 | 250,000 → −35,600 | 월 5회 × 기본요금 4,800 × 5% = 1,200원/월. Daily Plan 통합 한도 2.5만원을 택시 혼자 채울 수 없다 |

| 신한 B.Big / 편의점 | 230,000 → 20,000 | **note가 스스로 "실질 월 최대 2,500원"이라 적어 뒀다** |

**검산이 스스로 맞았다**: 신한 B.Big 편의점("실질 월 최대 2,500원") → 2,500, 같은 카드 통신비("실질 5천원") → 5,000,
토스뱅크 카페("월 10회를 다 채워도 1,000원이 상한") → 1,000. 카드사·기존 note가 적어 둔 실질값과 엔진 계산이 일치한다.

## 검증이 잡아낸 것

묶음마다 적대적 검증자를 붙여 30건을 지적받았다(blocker 2·major 10·minor 18). 주요한 것:

- **엔진 버그(내가 만든 것)** — `useGroup` 줄은 축소돼도 `effectiveCap`이 안 내려가 화면이 못 채울 한도를 약속했다
  ("120만원부터 한도 4만원"). 게다가 `clampGroup`이 새 객체를 돌려주는 탓에 첫 수정도 안 먹었다. 두 번 고쳤다.
- **`set`이 통째로 빠진 encode 2건** — reasoning은 축소를 계산해 놓고 적용할 값이 없었다.
- **`kbank-one-check`는 §4 위반** — 영역별 21,000 + 통합 25,000은 `capGroup`이 아니라 `sharedCaps`다.
  capGroup으로 누르면 여러 영역을 쓰는 사람이 연 48,000원 과소가 된다. 이관했다.
- **`shinhan-lottemart-maxx`는 통합 횟수** — 해부 원본이 「생활 할인 서비스 … 일1회·월5회」로 카페·배달앱을 묶어 놨다.
  한 줄에만 횟수를 걸면 카페 단독 사용자가 4배 과대로 남는다 → `useGroup`으로 묶었다.
- **stars를 실효 한도로 내리려던 것** — §8은 **rate 3~7%면 ★2**라 실효 한도가 줄어도 요율 밴드는 그대로다. 되돌렸다.

## 판단이 갈렸던 것

- **토스뱅크 체크 2단 요율(§10-3 적용)** — 원문이 "건당 1만원↑ 500원 / 3천~1만원 100원"인데 상위 단계로 인코딩돼 있었다.
  TXN_SIZE(카페 7,200·편의점 7,000)가 아래 단계라 낮은 단계로 내렸다(실질 5,000 → 1,000원, 5배).
  이는 C-1이 "선례가 모두 상위 단계라 일관성을 택했다"고 적어 둔 관행을 바꾼 것이다 — **그때는 기준값이 없어서 고른 관행이었고,
  이제 기준값이 생겼다.** §0-1('애매하면 낮은 구간')과도 맞는다.
  단 카페는 외식과 한 풀(capGroup 'food' 5,000원)을 나눠 쓰므로 **monthlyCap은 건드리지 않고** 요율·건당 조건으로만 표현했다.
- **`woori-everyday-check` 주유는 보류** — 규약대로면 300원까지 눌리는데, 주유 TXN_SIZE가 없어 minPerTx(자격 문턱 1만원)가
  그대로 건당 결제액이 되기 때문이다. 실제 1회 주유는 5만원대라 5~7배 **과소**가 된다. 기준값을 세울 때까지 횟수는 안 걸었다.
  **이 함정은 기준값 없는 태그 전반에 해당한다** — minPerTx는 '자격 문턱'이지 '전형적 결제액'이 아니다.

## 남는 한계

- **분포를 표현 못 한다.** 단일 상수로는 "결제의 몇 %가 문턱을 넘는가"를 못 적는다. 카페만 실측 분포가 있다.
- **범용·폴백 줄은 건당 조건을 반영하지 않는다**(대신 들어갈 줄이 없어서) — A-1과 같은 방향의 알려진 과대.
- **태그 내부 분산으로 일부는 과소다.** `ibk-kpass` 외식은 아웃백·빕스 전용인데 외식 평균 11,066원을 쓴다(실제 객단가가 훨씬 높다).
  택시도 기본요금 4,800원이라 실제 지불액(5.4km ≈ 7,700원)보다 낮다. 방향은 보수적이라 그대로 뒀다.
- **표현 불가**: "건당 N원 **이하**", "일 1회"(월 30회와 다르다), 회차 조건.
